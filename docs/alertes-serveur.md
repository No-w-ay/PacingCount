# Alertes serveur (Web Push) — note de chantier

> État au 2026-11-24 (beta.9) : **POC validée sur Android** (beta.2) ; logique des alertes (ensembles de types, rattrapage commun) codée côté local en beta.5, règle d'affichage unifiée en beta.6, interface de sélection multiple en beta.7, intégration réelle du serveur pas encore faite. La POC a validé : push programmé, reçu app fermée, annulation, ouverture de l'app au toucher ; test Android de 30 min OK. Test de 1 h, iOS et intégration réelle **pas encore faits**.
> Le dépôt est public : ne jamais y mettre de secret (clé privée VAPID, `.dev.vars`).

## 1. Pourquoi un serveur

Les alertes locales (`setTimeout` dans la page + Wake Lock + pseudo-veille + rattrapage au `visibilitychange`) ne fonctionnent plus si l'app est fermée. Un service worker ne peut pas garder de minuterie. Pistes écartées :
- **Notification Triggers API** : abandonnée par Chrome.
- **Periodic Background Sync** : trop grossier (intervalle imposé par le navigateur, pas d'heure précise).
- **Firebase / FCM comme produit** : inutile. Le Web Push standard (VAPID) suffit et évite un compte et un SDK supplémentaires. Les services push des navigateurs (Google, Mozilla, Apple, Microsoft) sont les mêmes qu'avec FCM.

## 2. Architecture retenue

Cloudflare Workers + Durable Objects (stockage SQLite, offre gratuite), dossier `cf-worker/` du dépôt.

- **Worker** (`cf-worker/src/index.js`) : réceptionniste public et sans état. Routes `GET /health`, `POST /schedule`, `POST /cancel`. Valide tout (origine, taille, types, limites) puis transmet au Durable Object de l'appareil.
- **Durable Object `DeviceAlarm`** : un par appareil (clé = identifiant aléatoire). Garde les horaires et l'abonnement push, programme **une seule alarme** (la suivante). À l'alarme : envoie le push, programme l'horaire suivant, efface tout après le dernier.
- **Push vide** : aucune donnée n'est envoyée au navigateur. Le texte de la notification est **fixe, dans `sw.js`** (`PUSH_TEXTS`). Ni le serveur ni un tiers ne peut faire afficher un message arbitraire.
- **Le téléphone calcule des horaires absolus** (ms depuis 1970) ; le serveur est « bête ». Il corrige le décalage d'horloge avec `clientNow`.
- **Sécurité VAPID** : clé publique dans `js/alerts-server.js` (publique par nature) ; clé privée uniquement dans les secrets Cloudflare (`VAPID_PRIVATE_KEY`, avec `VAPID_PUBLIC_KEY` et `VAPID_SUBJECT`). Les secrets ne se relisent pas : **garder une copie de la clé privée dans un gestionnaire de mots de passe**. En cas de perte : nouvelle paire, 3 secrets à refaire, clé publique à changer dans l'app, et tous les appareils doivent se réabonner.

### Protocole

| Appel | Corps JSON | Effet |
|---|---|---|
| `POST /schedule` | `{ deviceId, subscription: { endpoint, keys? }, clientNow, fireAt: [ms…] }` | remplace tous les horaires de l'appareil |
| `POST /cancel` | `{ deviceId }` | efface horaires et alarme |
| `GET /health` | — | contrôle de vie |

Limites actuelles : corps ≤ 4 Ko, ≤ 50 horaires, horaire ≤ 24 h dans le futur, ≤ 60 s dans le passé (envoi immédiat), `deviceId` = 22 à 64 caractères `[A-Za-z0-9_-]`, `endpoint` limité aux services push connus (Google, Mozilla, `*.push.apple.com`, `*.notify.windows.com`), TTL du push 300 s, 3 réessais espacés de 15 s.

### Robustesse du Durable Object
- Une alarme à la fois (`setAlarm` remplace la précédente). Une alarme est garantie **au moins une fois** : le code gère le doublon (garde de version, progression enregistrée **avant** l'envoi).
- Abonnement expiré (HTTP 404/410) : l'appareil est effacé. Échec passager : réessai. Rejet définitif : pas de réessai.
- Aucun identifiant dans les journaux ; erreurs génériques côté client.

## 3. Origines autorisées (CORS)

`ALLOWED_ORIGINS` dans `cf-worker/wrangler.toml` : `https://dev.pacingcount.pages.dev`, `https://pacingcount.pages.dev`, `https://no-w-ay.github.io` (main sur GitHub Pages). Une origine = schéma + domaine, sans chemin. Chaque origine est une app distincte pour le navigateur : un appareil a un abonnement push **par origine**, tous servis par le même Worker. Cette liste bloque les appels d'autres sites web ; ce n'est **pas** une authentification (un outil hors navigateur peut falsifier `Origin`). La vraie protection : identifiant d'appareil aléatoire, validation stricte, push vide.

## 4. Côté app (beta.1 à beta.12)

- `js/alerts-server.js` (ex `push-client.js`, renommé en beta.3) : abonnement (`pushManager.subscribe`, `userVisibleOnly`), envoi des horaires (`/schedule`), annulation (`/cancel`) et, depuis la beta.10, **synchronisation avec les vraies alertes** (`syncServerPlan()`, voir « Trois modes » en §7). `deviceId` dans la clé locale `pushDeviceId`, **hors export**, copié dans IndexedDB (le SW ne lit pas `localStorage`). **État de synchronisation = clé `push` d'IndexedDB, unique copie, lue et écrite par la page et le SW** : `{ deviceId, seq, endpoint, times }` (numéro de séquence, adresse d'abonnement connue du serveur, horaires confirmés) ; l'envoi (`alertsPushSync`) et ces fonctions sont dans `js/alerts-shared-sw.js`. La clé `pushSyncedTimes` de `localStorage` (beta.10-11) est supprimée au premier passage. Les boutons de test du POC (mode développeur) ont été **retirés en beta.10**.
- `sw.js` : charge `js/alerts-shared-sw.js` par `importScripts()` (dans un `try/catch` : un échec de chargement ne casse pas le service worker) ; écouteur `push` (`handlePush()`, voir §7), écouteur `notificationclick` (met l'app au premier plan, ou l'ouvre ; agit aussi sur les notifications locales), `showAlertNotification()` commun au message `DISPLAY_NOW` (page) et au push (serveur).
- `requestPermission` est appelé **en premier, de façon synchrone dans le clic** (obligatoire sur iOS) : c'est le clic sur le mode « Réveil via serveur » ou « Mixte » qui le déclenche (`onAlertModeChange()`, `js/alerts.js`).

## 5. Déploiement du Worker

Indépendant de Git : depuis `cf-worker/`, `npx wrangler deploy` (connexion `npx wrangler login`). `git push` ne met pas le Worker à jour. Secrets : `npx wrangler secret put <NOM>` ; liste : `npx wrangler secret list`. Test local : `npx wrangler dev` avec un fichier `.dev.vars` (ignoré par Git ; `ALLOW_NO_ORIGIN=true` pour tester avec curl). Syntaxe `[exports.DeviceAlarm] type = "durable-object" storage = "sqlite"` validée avec wrangler 4.x ; l'ancienne syntaxe `[[migrations]]` est gardée en commentaire dans `wrangler.toml` au cas où.
Le dossier `cf-worker/` est aussi publié par Pages comme fichiers statiques (aucun secret dedans ; absent de `ASSETS_TO_CACHE`).

## 6. Offre gratuite Cloudflare (vérifiée en novembre 2026 ; à revérifier avant la mise en production)

Workers : 100 000 requêtes/jour. Durable Objects (SQLite) : 100 000 requêtes/jour (alarmes comprises), 5 Go de stockage, 100 000 écritures/jour. Largement suffisant pour un usage personnel ou un petit groupe ; **pas de limitation par IP** à ce jour : un abus pourrait épuiser le quota (voir « À faire »). Dépassement : les opérations échouent **pour tous** jusqu'à 00:00 UTC. Coût estimé (non mesuré) : un envoi d'horaires = 1 requête Worker + 1 requête Durable Object + ~2 lignes écrites ; une alarme (push) = 1 requête + ~2 lignes. La limite la plus contraignante est celle des **lignes écrites** : avec ~10 envois et ~10 alarmes par utilisateur et par jour, soit ~40 lignes, le quota (100 000) correspond à environ 2 500 utilisateurs actifs ; 1 000 utilisateurs à 10 envois/h en continu le dépasseraient largement (usage irréaliste : l'app n'envoie que lorsque le plan change).

## 7. Décisions d'architecture

- **Deux canaux indépendants, activables séparément** (remplace l'ancienne idée de « deux modes exclusifs »), donc trois combinaisons : *local seul* (défaut), *serveur seul* (gardé au début pour pouvoir le tester), *mixte* (local + serveur : fiabilité maximale). À terme, on pourra ne garder que *local* et *mixte* (deux options visibles, la seconde recommandée) : facile si les trois sont bien en place. Partie commune = définition des alertes et interface.
- **Arbitrage du mixte (une alerte jouée une seule fois)** : il se fait sur l'appareil, sans coordination du serveur. (1) Clé d'alerte stable et identique pour les deux canaux (début de période + type + numéro de vague). (2) Registre « déjà jouée » commun à la page et au service worker, dans IndexedDB (le SW ne lit pas `localStorage`), avec « vérifier puis marquer » atomique. (3) Même `tag` de notification pour les deux canaux, `renotify: false` : la seconde remplace la première sans resonner. À vérifier sur appareil, surtout iOS.
- **Plan d'alertes commun** (fonction `computeAlertPlan`, faite en beta.4, dans `alerts.js`) : calcule le plan complet (clé, heure, texte) à partir des réglages ; ce plan est stocké dans IndexedDB. Le serveur ne reçoit que les heures. À l'arrivée d'un push vide, le SW retrouve l'alerte (donc son texte et sa langue) dans ce plan : le push reste vide, rien d'arbitraire ne peut être affiché.
- **Combinaisons de types (décidé le 2026-11-22, logique codée en beta.5, interface en beta.7)** : une alerte porte sur un **ensemble** de types : `{ id, typeIds: [..], threshold, interval, maxCount, enabled }` (migration automatique : `typeIds = [typeId]`, `id` stable ajouté, champ `wave` retiré). Le seuil se compte sur le **temps continu passé dans l'ensemble** : `getRunStart()` remonte l'historique depuis le début de la période en cours tant que la période précédente est **accolée** (écart ≤ `RUN_GAP_TOLERANCE_MS` = 1 ms, car `closePeriod` coupe à 23:59:59.999 à minuit) et de type dans l'ensemble ; passer d'un type à l'autre de l'ensemble ne remet rien à zéro ; arrêter l'enregistrement coupe la séquence. L'**absence** du type x s'exprime en cochant tous les autres types (pas de case « tous sauf ») ; sans période en cours, aucune alerte. Plusieurs alertes aux ensembles qui se chevauchent sont autorisées ; deux ensembles identiques : la seconde sauvegarde **remplace** la première. Registre « déjà jouée » (`state.sentAlerts`) : `{ alertId, runStart, waveIndex, firedAt, source: 'timer' | 'catchup' }` ; il est lié à la **séquence** (pas à la période), donc survit à un changement de type dans l'ensemble, et il est purgé quand la séquence se termine. Le plan pur (`computeAlertPlan(config, runStart)`) renvoie `{ index, fireAt, mins }` par vague. Interface (faite en beta.7) : le menu à un type est remplacé par des **pastilles à cocher** (une par type actif, plus les types inactifs déjà présents dans l'alerte éditée, estompés, en pointillés et marqués « (inactif) », décochables ; coche ✓ en plus de la couleur ; cible tactile ≥ 44 px). Nouvelle alerte : type de la période en cours pré-coché (à défaut type 4, puis premier type actif). Récapitulatif en direct, identique à la liste (`renderAlertSetHtml`) : **un type = une ligne « ● Libellé » ; plusieurs = ligne 1 les ronds reliés par « + », ligne 2 les libellés reliés par « + »**, sans troncature (retour à la ligne). Dans la liste, la ligne 3 porte les caractéristiques (« Après 30 min · +10 min · 3x ») à gauche, interrupteur et boutons ✏️ 🗑️ à droite. Aucun type actif coché : message « Choisissez au moins un type de période actif. ». Même ensemble qu'une autre alerte (ajout **ou** édition) : `confirm()` détaillant l'alerte qui serait remplacée ; si refus, le modal reste ouvert ; si accepté, l'autre est retirée (ajout : elle garde son id). Pas de case « tous sauf », pas d'ordre entre les types (c'est un ensemble). Libellés échappés (`escapeHtml`). À vérifier : élagage de l'historique, recalcul du plan après correction rétroactive de l'historique. Idée écartée : « absence depuis la fin de la dernière période d'un type » (l'ancien mode absence) — remplacée par les ensembles.
- **Types inactifs** : un type désactivé reste dans la définition de l'alerte ; l'alerte n'est désactivée que si **tous** ses types sont inactifs (et n'est pas réactivée automatiquement). Ids inconnus retirés ; ensemble vide → alerte supprimée (`syncAlertsWithTypes`).
- **Nom des alertes** : calculé, jamais stocké = libellés des types joints par « + » (`getAlertName`).
- **Textes des notifications (beta.5, sans emoji)** : rappel = titre *nom de l'alerte*, corps `{mins} min (rappel {n}/{total})`. **Rattrapage commun à toutes les alertes** (`tag` `pacing-catchup`) : une alerte → titre `Rattrapage : {nom}`, corps `{mins} min (rappel n/total)` ; plusieurs → titre `Rattrapage : N alertes`, une ligne par alerte `{mins} min · {nom} (rappel n/N)`, triées par durée décroissante (tri stable : à égalité, ordre de la liste des alertes). Le mot « catchup » n'apparaît plus ; le rattrapage reste un concept unique, explicite.
- **Règle unique d'affichage `playDueWaves()` (beta.6, local ; le SW appliquera la même règle au push)** : appelée par chaque minuterie et au retour visible. Elle prend les vagues dues et non jouées de toutes les alertes. Une alerte avec **une seule** vague due, en retard d'au plus la tolérance → rappel normal. Tous les autres cas (plusieurs vagues dues, ou retard plus grand) → **un seul** rattrapage commun. Vagues **marquées avant l'attente du SW** (pas de doublon ni de désordre quand plusieurs minuteries se réveillent ensemble au dégel de la page) ; marquage annulé si le SW est introuvable. Cause du défaut vu en beta.5 : deux chemins (minuteries < 120 s en rappels séparés, rattrapage > 120 s) aux règles différentes, qui se couraient l'un après l'autre.
- **Tolérance de retard : 60 s** (`ALERT_LATE_TOLERANCE_MS`, uniforme local et serveur ; passée de 120 s à 60 s en beta.6 d'après le test sur appareil ; 60 s = intervalle minimum de l'interface, donc une alerte n'a jamais deux vagues dans la tolérance). Le retard réel est journalisé (`[playDueWaves]`) pour calibrer. Pas de rattrapage au démarrage de l'app pour les vagues anciennes (comme avant). Remplace l'ancien seuil de 15 s (local) et le code des « vagues croissantes » (supprimé, ainsi que le bloc HTML commenté).
- **Plan stocké sur l'appareil (beta.8, sans consommateur pour l'instant)** : `js/alerts-shared-sw.js` (ex `alerts-store.js` ; IndexedDB `pacingcount-alerts`, magasin `kv`, sans `window` ni `document` : chargeable par le SW via `importScripts` en beta.10). `buildServerPlan()` construit `{ v: 1, lang, texts, waves[] }` : toutes les vagues (passées et futures) de la séquence en cours, chacune avec `alertId, alertOrder, name, runStart, index, total, mins, fireAt, tag, title, body` ; `texts` garde les modèles du rattrapage avec leurs `{variables}` (le SW ne connaît que nom, durée et rang au moment d'afficher). Pas d'horodatage de construction : deux plans identiques donnent le même JSON, donc `refreshAlertPlanStore()` n'écrit que si le plan a changé. Appelée à chaque `scheduleAlerts()`, à chaque `cancelAlerts()` (plan vide, et non absent, pour que le SW distingue « aucune alerte » de « jamais écrit ») au passage en arrière-plan, au changement de langue (`changeLang`) et à l'enregistrement des réglages (`saveSettings`, renommage d'un type). IndexedDB indisponible : avertissement en console, l'app continue en local. Vérification sur appareil : console, `await alertsStoreGet('plan')`.
- **Socle partagé page / service worker (beta.9, aucun changement visible)** : un seul fichier `js/alerts-shared-sw.js` (en-tête de fichier : règle « pas de DOM, pas de réglages ») regroupe le stockage IndexedDB, le registre partagé et la règle commune ; il remplace `alerts-store.js` (4 fichiers d'alertes au total : partagé page/SW, commun page, local, serveur). **Une seule règle** : `alertsSelectDue(waves, played, now)` (vagues dues, rappel normal si une seule vague due et retard ≤ 60 s, sinon rattrapage) et `alertsBuildCatchup()` (texte d'après les modèles du plan) sont utilisées par `playDueWaves()` de la page et le seront par le service worker ; `buildCatchupText` est supprimée. **Registre « déjà jouée » en deux copies** : `state.sentAlerts` (page, synchrone : marquage avant l'attente d'affichage) et IndexedDB clé `played` (lisible par le SW). La page recopie chacun de ses changements (ajout, retrait, nettoyage de séquence, `cancelAlerts`, `forgetSentAlerts`) ; au début de chaque `playDueWaves()`, `mergePlayedFromStore()` ajoute à la copie de la page ce qu'un autre acteur a joué (attente limitée à 0,8 s : une IndexedDB muette ne bloque jamais une notification). La fusion est une union, sans conflit : une vague jouée n'est jamais « dé-jouée » hors nettoyage de fin de séquence. Les écritures dans IndexedDB lisent puis écrivent dans **une seule transaction** (`alertsStoreUpdate`), donc la page et le SW ne peuvent pas s'écraser. En cas d'écriture ratée, au pire une vague est rejouée une fois ; même `tag`, la notification remplace la précédente au lieu de s'empiler. Limite connue : au retour arrière d'un import JSON (`savedSent` dans `import-export.js`), la copie de la page est restaurée mais pas celle d'IndexedDB (même conséquence : au pire une vague rejouée une fois).
- **Trois modes des alertes (beta.10)** : réglage `settings.alertMode` = `'local'` (défaut, nom affiché « Hors ligne »), `'server'` (« Réveil via serveur ») ou `'mixed'` (« Mixte ») ; `getAlertMode()` renvoie `'local'` pour toute valeur absente ou invalide. Le mode est aussi écrit dans le plan stocké (`plan.mode`) : **le service worker ne joue un push que si le mode est serveur ou mixte** (sinon c'est un push périmé). Le réglage n'est **pas** importé / exporté avec les données (il dépend de l'appareil : abonnement push, autorisation). Interface : zone « Mode des alertes » en haut de la section « Alertes de périodes » des réglages (3 choix avec description, ligne d'état de la synchronisation, mention de confidentialité visible hors mode local). Serveur et Mixte sont **grisés** avec la raison affichée si le push n'est pas pris en charge (sur iOS : app installée sur l'écran d'accueil) ou si les notifications sont refusées. Choisir Serveur / Mixte demande l'autorisation et crée l'abonnement **dans le clic** ; en cas d'échec, le mode précédent est conservé et un message explique pourquoi.
  - **Comportement de la page** : *local* = comme avant (minuteries, Wake Lock, rattrapage au retour), aucun contact avec le serveur. *Mixte* = idem + synchronisation des horaires avec le serveur ; **repli Wake Lock** : l'écran n'est retenu que tant que le serveur n'a pas confirmé (`pushSyncStatus !== 'ok'`), relâché dès la confirmation ; `scheduleAlerts()` reste la source de vérité du Wake Lock et est rappelée à chaque changement d'état. *Serveur* = ni minuterie, ni Wake Lock, la page ne joue rien (même au retour au premier plan) : seul le serveur réveille l'appareil.
  - **Synchronisation** (`syncServerPlan()`) : horaires voulus = heures (sans doublon) des vagues futures non jouées de la période en cours, de +1 s à +23 h 50 (le Worker refuse au-delà de 24 h ; les vagues plus lointaines sont envoyées à la prochaine ouverture de l'app), 50 au plus ; liste vide en mode local ou sans période. Comparés aux horaires déjà confirmés (`pushSyncedTimes`, privés des horaires passés) : **aucun envoi si rien n'a changé** (une vague qui passe n'en provoque pas). Liste vide → `/cancel` ; sinon `/schedule` (qui remplace tout). **Jamais de contact avec le serveur tant que l'utilisateur n'a pas choisi Serveur ou Mixte** (jamais synchronisé + rien à envoyer : on mémorise `[]` sans réseau). Appelée : après chaque écriture du plan, au changement de mode, au démarrage, au retour au premier plan, à l'événement `online`, et toutes les 2 min tant que l'état est « en attente ». Une seule passe à la fois (appels simultanés regroupés). États : `unknown` / `ok` / `pending` (hors ligne ou serveur injoignable) / `unavailable` (push impossible ou refusé) / `idle` (mode local).
  - **Push reçu (`handlePush` dans `sw.js`)** : le SW lit le plan et le registre dans IndexedDB, applique `alertsSelectDue()` (même règle que la page : rappel normal ou rattrapage groupé), **marque les vagues (source `'sw'`) avant d'afficher**, puis affiche avec les textes pré-traduits du plan (même tag que la page : la seconde notification remplace la première). Rien de dû (push en avance, périmé, déjà joué, mode local, plan absent) : fenêtre de l'app visible → rien ; sinon notification silencieuse **fermée aussitôt** (*show-then-close*, **à valider sur appareils, iOS compris**). Dernier recours (code partagé non chargé, IndexedDB illisible, affichage en échec) : notification neutre fixe, tag `pacing-push-fallback`, dans la langue du navigateur.
  - **Confidentialité** : la phrase affichée sous les modes en beta.10 a été **retirée en beta.12** (un message général sur la vie privée existe ailleurs dans l'app). Contenu réellement envoyé au Worker, vérifié par test : `deviceId`, `subscription`, `clientNow`, `fireAt`, `seq` : aucun nom de période ni donnée de santé.
  - **Beta.12 : fiabilisation de la synchronisation.** (1) **Numéro de séquence** : chaque envoi (`/schedule` ou `/cancel`) porte un numéro croissant, pris dans l'état partagé (IndexedDB, incrémenté dans une transaction : page et SW ne peuvent pas obtenir le même). Le Worker refuse (409 `stale`, avec son dernier numéro) un envoi dont le numéro n'est pas supérieur au dernier accepté : un vieil envoi retardé par le réseau ne peut plus écraser un plus récent. Le numéro est conservé séparément de l'état : il survit à l'annulation et à la fin d'un programme. Le champ est **facultatif** côté Worker (anciennes versions de l'app acceptées). Si le compteur local est perdu (stockage effacé), la réponse 409 permet de se recaler (un réessai). (2) **Remise à jour par le SW** : après chaque push (même « rien de dû »), `resyncServerAfterPush()` recalcule les horaires restants d'après le plan et le registre, et renvoie `/schedule` ou `/cancel` s'ils diffèrent de l'état connu. Elle passe **après** l'affichage, en « au mieux » (erreur ignorée). Elle aide quand le serveur a déjà reçu au moins un horaire (fenêtre de 24 h qui avance, envoi précédent resté sans réseau) ; **si le serveur n'a rien reçu du tout, aucun push n'arrive et le SW ne se réveille pas** : c'est le repli Wake Lock du mode mixte qui couvre ce cas. (3) **`pushsubscriptionchange`** : le SW se réabonne avec la même clé VAPID et envoie la nouvelle adresse ; filet côté page (support inégal selon les navigateurs) : l'adresse d'abonnement est mémorisée avec les horaires, et une adresse différente déclenche un renvoi même si les horaires n'ont pas changé. (4) **Limite par appareil** dans le Worker : 30 appels (`/schedule` + `/cancel`, refusés compris) par heure, compteur en mémoire du Durable Object (aucune écriture), réponse 429 + `Retry-After` ; la page traite 429 comme « en attente » (nouvel essai plus tard). Elle protège contre un client défaillant ; **elle n'arrête pas quelqu'un qui change d'identifiant d'appareil à chaque requête** (piste : règle de limitation par IP côté Cloudflare, disponibilité sur l'offre gratuite à vérifier).
  - **Interface (beta.12)** : icône d'état à côté du nom du mode serveur / mixte choisi (✔ vert = serveur à jour, 📶? orange = connexion à vérifier avec nouvel essai automatique toutes les 2 min, ✖ rouge = indisponible : push non pris en charge ou notifications refusées, l'utilisateur doit agir) ; texte dans l'info-bulle et `aria-label` ; la raison d'un blocage reste en texte sous les choix. Conditions de chaque mode en gras. 📶 plutôt que 🛜 (Unicode 15, absent des appareils anciens).
  - **Limites connues** : en mode *serveur*, si l'autorisation est retirée plus tard ou si le serveur reste injoignable, **aucune alerte ne sonne** (l'icône et la raison le signalent) ; le mode *mixte* évite ce risque tant que l'app reste ouverte. Deux push reçus exactement ensemble pourraient afficher deux fois la même vague (même tag : la seconde remplace la première). Le nouvel essai toutes les 2 min est sans limite de nombre (coût négligeable : hors ligne, aucune requête ; en ligne mais serveur en panne, au plus ~30 requêtes/h ; la page gelée en arrière-plan n'essaie presque pas) ; un espacement progressif a été écarté (bénéfice négligeable, complexité inutile). Si le serveur et le SW calculent des horaires différents au même moment, le dernier numéro gagne (les deux dérivent du même plan).
- **Push vide arrivant « trop tôt » ou périmé (décidé le 2026-11-23 ; étapes (1) à (3) codées en beta.10, remise à jour du serveur par le SW en beta.12)** : le push ne dit jamais quoi jouer ; le service worker **décide d'après le plan stocké localement** (IndexedDB), pas d'après le push. À la réception : (1) chercher dans le plan les vagues dues (`maintenant ≥ fireAt − ~10 s`) et pas encore jouées d'après le registre ; (2) s'il y en a, les jouer (une seule notification groupée si plusieurs, comme le rattrapage) et les marquer ; (3) s'il n'y en a aucune (plan modifié hors ligne, alerte supprimée, push arrivé avant l'heure), **ne rien jouer d'avance**. Contrainte : `userVisibleOnly` oblige à afficher *quelque chose* (Chrome affiche sinon une notification générique, iOS révoque l'abonnement après des pushs silencieux). Piste à tester sur appareils : afficher puis fermer aussitôt la notification (*show-then-close*) ; **à valider en particulier sur iOS**, plus strict. **Remise à jour du serveur** : dans ce cas le SW renvoie lui-même `POST /schedule` avec le plan local (ou `/cancel` si vide) ; sinon la page le fait au prochain démarrage ou retour au premier plan. La page tient un **indicateur « synchronisation en attente »** (positionné à chaque modification du plan, effacé quand le serveur a confirmé), relancé à l'événement `online`, au retour au premier plan et au démarrage. Option : un numéro de séquence croissant envoyé avec chaque plan, pour que le serveur ignore un plan plus ancien arrivé en retard. Les textes sont **pré-traduits par la page** et stockés avec le plan (le SW n'a pas `translations.js`).
- **Modification ou suppression d'une alerte** : l'app recalcule le plan complet et renvoie toutes les heures (`/schedule` remplace tout) ; liste vide → `/cancel`. Aucun identifiant d'alerte côté serveur.
- **Wake Lock, pseudo-veille et message d'avertissement** : n'ont de sens qu'en *local*. En *mixte*, une fois le serveur à jour, le Wake Lock est relâché (économie de batterie) ; il est repris si la synchronisation est en attente (codé en beta.10). Le message d'avertissement des notifications n'a pas encore été adapté aux modes.
- **Alerte fantôme** : si une annulation ou une modification n'atteint pas le serveur (hors ligne), un push périmé peut arriver. Le SW doit toujours afficher une notification (iOS révoque l'abonnement sinon). Parades : annulation mise en file d'attente et rejouée au retour du réseau, horizon des horaires limité. Vaut aussi pour *serveur seul*.
- **Trois fichiers** (fait en beta.3, simple déplacement sans changement de comportement) : `js/alerts.js` (commun), `js/alerts-local.js` (mode local), `js/alerts-server.js` (mode serveur, ex `push-client.js`). Choisi plutôt qu'un fichier unique : le mode local (Wake Lock, pseudo-veille, minuteries) est isolé et pourra être retiré ; le calcul des horaires (présence / absence, appelé à évoluer) restera dans le fichier commun, partagé par les deux modes. Le choix local / serveur se fera dans les points d'entrée communs (`scheduleAlerts`, `cancelAlerts`, `releaseWakeLock`), encore dans `alerts-local.js` pour l'instant.
- Question ouverte : période démarrée hors ligne en mode serveur (horaires à envoyer dès le retour de la connexion ?).
- Texte des vraies alertes : **tranché et codé en beta.10** (voir « Push vide arrivant trop tôt ») : textes pré-rendus par la page, stockés avec le plan dans IndexedDB, push toujours vide. `PUSH_TEXTS` (POC) est supprimé de `sw.js`.
